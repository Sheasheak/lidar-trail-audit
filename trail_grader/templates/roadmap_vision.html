AI Trail Camera Integration

Bare-earth LiDAR grades gradient, turn radius and cross-slope with high confidence — but it can't see roots, loose rock, jump lips, or surface condition, because those sit above the bare-earth model entirely. This page tracks the production-grade computer-vision pipeline intended to close that gap: a rider-mounted or trailside camera feed, automatically flagging technical features and hazards, fused into the same grading output as the LiDAR layers.

Honest status: nothing on this page is built yet. This is the architecture TrailSafe is designing toward, published so DOC and anyone else following the project can see the actual shape of the plan — and where it's currently stuck — rather than a vague "AI camera, coming soon." A much smaller, faster prototype (sampling GPS-tagged frames through an existing vision-capable language model, no custom training) is the realistic near-term step; it isn't what's documented below.

Stage detail

What each stage needs, and what's blocking it
01

Capture

Planned

Rider-mounted or trailside camera footage, GPS-synced so every frame can later be placed at a chainage position along the same trail line LiDAR already samples. Action cameras with onboard GPS (GoPro GPMF metadata, phone-logged tracks) make this the most tractable stage — it's closer to data logistics than research.

Needs
  • GPS-tagged footage source (rider-mounted or fixed trailside units)
  • A consistent upload path into TrailSafe
Open questions
  • Rider-mounted (per-audit, variable coverage) vs fixed trailside cameras (continuous, costly to deploy at scale)
  • Storage cost of raw video at any meaningful trail-network scale
02

Chainage alignment

Planned

Matching each frame's GPS fix to the nearest station on the already-sampled trail line, so a detected hazard lands on the same 1 m chainage grid as the gradient/radius/sideslope data — not a separate, disconnected location system.

Needs
  • GPS accuracy/drift correction (consumer GPS can be several metres off under canopy)
  • A snap-to-line routine against the existing trail geometry
03

Detection model

Research

The actual computer-vision model: given a frame or short clip, classify trail-specific hazard and feature classes — roots, loose rock, jump lips, drops, erosion, surface type. This is the stage that decides whether the whole pipeline is worth building, and it's the one with no settled answer yet.

Candidate approaches
  • Custom-trained detector (YOLO-family or similar) on trail-hazard classes — fast at inference, needs labelled data
  • General-purpose vision-language model prompted per frame — needs no training, far higher per-frame cost, unproven accuracy on trail-specific hazards
Open questions
  • Real-time (on-device/edge) vs batch processing of uploaded footage after a ride
  • Accuracy target before a flagged hazard is trustworthy enough to act on unreviewed
04

Training data

Blocked

The actual bottleneck. A custom detector needs a labelled dataset of NZ mountain bike trail footage with hazards and features annotated frame-by-frame — roots, rocks, jump lips, surface condition. No such public dataset exists. Building one means filming a representative spread of trail types and grades, then manually labelling it, which is a slow, unglamorous prerequisite that has to happen before stage 03 can move past "research."

Needs
  • A trail-footage corpus spanning grades 1–6 and surface types
  • A labelling scheme matching the hazard/feature classes stage 03 needs
  • Volunteer or paid annotation effort — this doesn't automate
05

Fusion with LiDAR grading

Planned

Feeding detected hazards into the existing grading pipeline as a field-observation layer, the same role manual field notes play today — shown on the map alongside the gradient/radius/sideslope layers already live, at the chainage stage 02 computed, instead of a separate report.

Already built, reusable
  • The out-of-grade map-layer/toggle pattern (gradient, turn radius, sideslope)
  • Manual field-note pin dropping — the interim version of this, already live
06

Field review UI

Planned

Automated detection won't be trusted unreviewed from day one — an inspector needs a fast way to confirm or dismiss each flagged frame before it counts toward a grade. This is the human-in-the-loop layer that makes an imperfect model usable in practice.
